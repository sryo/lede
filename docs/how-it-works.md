# How Lede works

Lede is one Cloudflare Worker that counts the people who visit your site and tells you, in plain words, what changed.

## Deploy from the command line

Turn on Analytics Engine once for your account: in the Cloudflare dashboard, Storage & databases, Analytics Engine, Enable. Then:

```bash
npx wrangler deploy
npx wrangler secret put DASHBOARD_PASSWORD
npx wrangler secret put ANALYTICS_TOKEN
```

For the token, [create one with this link](https://dash.cloudflare.com/profile/api-tokens?permissionGroupKeys=%5B%7B%22key%22%3A%22account_analytics%22%2C%22type%22%3A%22read%22%7D%2C%7B%22key%22%3A%22account_settings%22%2C%22type%22%3A%22read%22%7D%2C%7B%22key%22%3A%22browser_rendering%22%2C%22type%22%3A%22edit%22%7D%5D&accountId=%2A&zoneId=all&name=Lede). It comes with the three permissions Lede needs: Account Analytics Read (to read the stats), Account Settings Read (to find your account) and Browser Run Edit (to take a picture of a page for its view). Check the form lists all three before you create it; if Browser Run is missing, add it with Add more, Account, Browser Run, Edit. A token without it still works, and the page's view says how to add it.

The first deploy creates the `STORE` KV namespace and the `Live` Durable Object (see Pieces). The Analytics Engine dataset is created when the first event arrives. Open the Worker's address, type your site's address, and add the line it shows to every page:

```html
<script defer src="https://lede.<your-subdomain>.workers.dev/t.js"></script>
```

Blocklists that keep tracker scripts from loading list `workers.dev` addresses, Lede's among them. When your site is on Cloudflare in the same account, you can serve Lede from your site's own address instead: add two routes to the Worker, `example.com/t.js` and `example.com/lede*` (in the Cloudflare dashboard, Workers & Pages, lede, Settings, Domains & Routes, Add, Route; or `"routes"` in `wrangler.jsonc`), then use `<script defer src="/t.js"></script>`. The tracker sends to the address it was loaded from, so nothing else changes. `t.js` through the route is still a static asset, which Cloudflare doesn't charge for; `/lede` is a Worker request either way.

Lede reads your account ID from the token. If the token works for more than one account, run `npx wrangler secret put ACCOUNT_ID` and paste the ID of the account Lede runs on. To find it, open that account in the Cloudflare dashboard: it's the long code after `dash.cloudflare.com/` in the address.

An empty `DASHBOARD_PASSWORD` (or one of only spaces) counts as none, and the dashboard opens without one.

When something goes wrong (a query Cloudflare refused, a webhook that didn't answer, a picture that couldn't be taken), Lede says what and what to do next in the Worker's logs: in the Cloudflare dashboard, Workers & Pages, lede, Observability, kept for 3 days. `npx wrangler tail` shows them as they happen. Only Lede's own lines are kept, not one for every request (`observability` in `wrangler.jsonc`), so page views don't use up the free plan's 200,000 log lines a day.

The dashboard isn't for search engines: `public/robots.txt` turns every crawler away, and every answer but `t.js` says `X-Robots-Tag: noindex`.

## Run it locally

```bash
npm install
npm run dev
```

Open http://localhost:8787. `npm run dev` serves sample data, so no Cloudflare account is needed: it runs with `--local`, which leaves out Workers AI (it has no local stand-in, and would need a login), so the sample's second line under the sentence is fixed text from `src/demo.js`. `npm test` runs the tests.

`npm run demo` builds a static copy of the same sample into the system's temporary folder (it prints where; `--out` picks another): the dashboard, plus the Worker bundled for the browser with `DEMO="true"`, which answers the dashboard's `/api/*` calls from the sample data in the page itself. The workflow in `.github/workflows/demo.yml` publishes it to https://sryo.github.io/lede/ on every push to `main`, so the demo costs nothing on Cloudflare and visitors can't use up its free limits. The copy has no sign-in, calls no Workers AI (the second line is the sample's fixed text), can't make read-only links, and keeps saved goals, funnels and notes in memory until the page reloads. The repo's owner has to turn Pages on once, in Settings, Pages, with Source set to GitHub Actions; until then the workflow stops before it publishes anything. The workflow runs only in `sryo/lede`, so the copy the Deploy to Cloudflare button makes in your own account skips it.

## The dashboard

Until the site has had its first visit, home shows the line to add to every page instead. After that it always draws: a period with nobody in it says how many came the period before, and to check that Lede's line is still on every page.

Home leads with the visitor total and a sentence saying what changed and where it came from, then today so far and a small crowd of who is here now, then four tiles: Visitors per day (against the days before), Where visitors came from, and the pages they landed on (when the visits the sentence's source sent to its page left after that page 10 points or more above or below the site, with 50 visits or more, the page says so under its name: "6 in 10 of them left"), Did they stay (bounce as rows of ten squares, how long a visit lasts, and, when bounce held, the source whose visits bounce most, 10 points or more above the site with 50 visits or more) and Pages by visitors (the pages the sentence and the caption name are the solid ones). A block gives its page's name in lines broken after a `/` or `-`, or at a syllable with a faded hyphen, level from the top-left or turned to read up a tall block from the bottom-left, at the biggest type, down to 10px, that shows the most of it; a name that still doesn't fit keeps its start and its end and is cut in the middle, and the whole name is in the block's hint. Open any tile, block, ribbon or underlined name to see more; Esc goes back. The crowd of who is here now draws one figure a person while everyone fits in three rows; past that, each figure stands for the smallest of 2, 5, 10, 20, 50… people that fits, and the caption says so ("a figure is 10 people"). The figures are shared in proportion between those here from a source the sentence names, the rest here and those who left, and a group with anyone in it always gets one, so no one is rounded away. Colour says what kind of thing a mark is: visitors over time are blue, sources amber, pages violet, bounce red, people here now green.

Under the sentence, home can add a second line that links what the sentence can't fit, such as where one source's readers landed, how long they read and how fast that page loads: "Lede noticed: Readers stay longest on /owls, 1m 40s, and it is also slow to load, LCP 4.7 s and INP 560 ms. Worth checking: what /owls loads first." Workers AI writes it from the totals Lede already worked out, and Lede checks it before it shows; see [The second line](#the-second-line). It comes after home has drawn, and when there's none, nothing shows.

Every view has its own address, so refresh and the back button work and a link opens the same view: `/overview`, `/bounce`, `/online`, `/events`, `/sources`, `/pages`, `/sources/google.com` (`/sources/direct` for no referrer), `/channels/ai`, `/page/docs/install` (`/page/` is the home page). `?days=7` and, with more than one site, `?site=` ride along. See `public/routes.js`. Old `/keywords` and `/funnels` links open the overview. A source's address with a channel on it (`/sources/google.com?channel=search`) opens the source's own view; the channel is dropped.

The Online view draws a lane for each page, those with most people here first (past 8 pages, the busiest 7 and then the rest together in one lane), and stands each person along it by how long they've been on the site, on a scale that gives the first minutes the most room and ends at 30. Those who left are pale; someone from a source home's sentence names is amber. When a lane would crowd, or more people came than the list holds, each lane is drawn in four bands instead, under 1, 5, 15 and 30 minutes, with each figure the same number of people in every lane so pages compare, said in the key. Its sentence says where the people on the site past 5 minutes came from, and the key under it counts those here now and those who left.

Who is here now refreshes every minute, and when you come back to the tab: on home, and on the Online view while it's showing. The Online view leads with the page most of those here are on, when there is one, since a crowd on one page is the news, and says whether the last 30 minutes are usual for this time of day: half the visitors of this hour on the same weekday earlier in the last 30 days, from the hours home already loaded ("87 came in the last 30 minutes, about usual for this hour"). Under the lanes, a row per lane gives each person here a line while there are 5 or fewer on the page and the list holds everyone; past that, one line counts those here by source, the top three and how many more sources. Those who left are one count per page, by source, either way. Everyone in the last 30 minutes is counted, but the list holds the 200 seen last, so the answer stays small however big the crowd; the counts, by page, source and how long on the site, cover everyone. liveSql reads 1,000 page views at most, so an answer that reaches them, and the live object for half an hour after a seed that did, says its counts are a floor: "400+ here now", "At least 400 people are here now". Home and today so far always read the last 30 days of hours, whichever period is showing, so the 7 and 30 day views agree on today.

Every view leads with a finding of its own. Home's sentence says what changed, so the overview leads with what stood out in the period: the big day, with the note you left on it, then the kinds of the other things ("Three more things stood out: a new source, a new page and a quiet day."). What happened lists every item, so its sentence names their kinds. The overview's cards go from the story to the details: visitors per day, What happened, Where readers came from and what they read (a strip of shares for sources and one for pages, led by what home's sentence left out on each side, from the rows home already has), Keywords, where readers are, By weekday and hour (led by when readers come: "Readers come most on weekday mornings, 7:00–10:00; the busiest hour is Tuesdays at 9:00", named when three hours in a row hold a quarter of the visitors, and marked on the chart), Funnels, and Links people clicked (led by the most clicked, as a share of all visitors, and the link whose clicks rose most). A share that rounds to 0% but isn't nothing reads "<1%".

The Sources screen's waterfall names the three sources that moved most, AI assistants as one when more than one sent visitors, then Everyone else, the rest of the change, and its sentence says how much of the change they made ("Three sources brought 9 in 10 of the 7,283 extra visitors: google.com, AI assistants and facebook.com"), then a new source that isn't among them. The list of sites says which channel each is in. A source's view adds, under its sentence, the page that moved most with its readers and a page they read far more than everyone does (a tenth of them, half again everyone's share); a channel's view lists the sources in it; Direct's view says what Direct means. Its Did they stay card gives how long a visit lasts beside the site's. The Pages screen leads with the page that moved most, and its list of pages viewed says how long half of each page's readers stay. Read or skimmed, above the list, places every page by how long half its readers stay (on a log scale) and how far down they get on average, its dot as big as its views read for a second or more. Dashed lines at the site's medians, over the pages with 20 read views or more, cut four corners: read to the end, skimmed to the end, stayed near the top, left early. A page with fewer views is a hollow dot, left out of the medians and the sentence; a page slow to load (poor LCP on 30 measures or more) has a red ring. Its sentence names the page read longest and, when it is read for less than most pages, the page opened most ("/owls is read longest: half its readers stay past 1m 37s, and it is slow to load, 4.7 s. The home page is opened most but read for less than most pages, 22s."). With fewer than 3 pages of 20 read views it says there are too few to compare. It comes from the engagement rows the list already reads, with no query of its own.

The Bounce screen draws where visits came from, the page they landed on and whether they read on or left after it as a Sankey of three columns, all in visits so the third adds up to the first: the five busiest sources and pages, the rest as "other". Its sentence names the source and landing page whose visits bounce most beyond the site, by the same rule as the standout below (50 visits or more, 10 points or more above the site, most extra bounces), and draws that pair's ribbons solid: "Of the 14,966 visits google.com sent to the home page, 5 in 10 left after that page, against 4 in 10 across the site." With none it says no pair stands out, and under 30 visits that there are too few. It reads the flows home already loads, which carry each pair's visits and bounces. Then it draws each source and landing page as a row of ten squares, as home does, with its visits beside it, so a high rate on a few visits reads as what it is. When bounce held, it names who bounces most beyond the site's rate, as home's tile does.

Setup, beside Share, holds what an owner needs once in a while: Lede's line to copy, a field to count another site, the tab icon, whether messages are on (and the command that turns them on), and Sign out when there is a password. None of it is a setting Lede needs to work.

The tab shows Lede's mark in one of nine colourways, so tabs for different sites tell apart. Each site gets the one its name hashes to, so the same site looks the same in any Lede that counts it; within one Lede, a site whose colourway an earlier site in the list took gets the next one free. Setup shows the nine and keeps the owner's pick for the site, for everyone who opens its stats, and Automatic goes back to the name's. The pick is saved with the site's goals, so it costs no read of its own and one write when it changes. The icon added to a phone's home screen stays Lede's own.

Near the end, the overview shows where readers are and what they use. It leads with the one thing worth saying, picked by a rule in `audienceStory` (`public/story.js`): a country, device or browser whose share of readers moved by 2 points or more and which itself moved beyond noise (so a country that only grew along with the whole site doesn't count), or phones and computers, each with at least 50 visits, bouncing 10 points or more apart ("Most readers are on phones, and readers on phones leave sooner: 62% of their visits bounce, against 38% on computers."). When several qualify, the one that moved the most readers wins: for a share, the readers it moved; for bounce, the visits on the worse device times the gap. With none it says "Nothing stands out about where readers are or what they use.", and with fewer than 30 visits "Too few visits yet to say much about where readers are or what they use." Below it, countries, devices and browsers each get one strip of shares: the top four (and whatever the sentence names), then the rest together; hover a part for its visitors and the change. Unknown countries and "Other browsers" are never the finding.

Visits stored before Lede recorded devices and browsers have neither, so they count for countries only. While either period holds some, devices and browsers show no change, and a line under the card says which period was only partly recorded.

A page's sentence weighs its change against the whole site's when they differ by 5 points or more ("up 20%, against 10% for the whole site"), and adds that it is slow to load once its speed says so. With goals set, its numbers add how many of the visits that saw it went on to reach one, against all visits, counted from the same rows as where readers went next. The home page is never offered as a goal. A page's view shows Time on page (the median time people had it open and in view: half the views were shorter), a line for how fast it is (see Page speed under What each number means) and How far down people scroll, then a sentence saying where half the readers have stopped and naming the tenth where more stop than anywhere else, beside a picture of the page itself, shaded darker further down as fewer readers are still there, with a violet line at that tenth. Under 50 views it says how few views that is, gives counts ("6 of 12") where it would give shares, and names no tenth.

The picture is taken by Cloudflare's Browser Run (`src/shot.js`), in your own account, only when someone opens a page's view: once per page a day, or once a minute at most while Cloudflare's browser is busy, kept in KV for a day. Lede keeps to 5 minutes of browser time a day, half of the free plan's 10, and a picture takes a few seconds of it, so dozens of pages a day can get one. Past that, or when a picture can't be taken, it shows the picture the page shares on social sites (its `og:image`), or else, in place of the picture, the share of readers still there either side of the drop and at the end, and says Lede takes one tomorrow; when Cloudflare couldn't take one, it says so. When Cloudflare's browser is busy (it answered 429 or a 5xx without spending browser time, or not at all), the next open a minute or more later tries again; an answer that did spend browser time (a page too slow to load, say) counts toward the 5 minutes and isn't tried again that day. Two 429s a minute or more apart, with no picture between them, mean the account's own browser time for the day is gone, so Lede takes no more pictures until the next day (UTC). A picture already taken is never replaced by a failure. When the token lacks the Browser Run permission it says to add it. The share picture is read only from an HTML page, and only from its first 300 KB. The sentence and those numbers never wait for the picture, which takes their place when it comes. The browser that takes it never loads `t.js` from Lede's address, and its visits are dropped anyway (see What isn't counted), so a picture is never a visit. Pictures are 1280 pixels wide, drawn at half size; a page so long its picture passes 2 MB gets none. The demo has a small picture of /owls only (every Worker carries it, so it's kept under 16 KB).

A page's view also draws the page as a crossing: where its readers came from on the left (the top four sources of visits that landed on it, the rest, and visitors who came from another of your pages), counted in visitors, where they went next on the right, as a share of the page's views (the top four pages viewed straight after it, the rest, and "Left the site" when it was the visit's last page), led by a sentence such as "After /pricing, 38% leave the site and 22% go on to /signup." Under 20 views it gives counts instead of shares. A change in how many leave is mentioned when it is at least 5 points and well clear of chance. A page's view and the overview end with the links people clicked (Links people clicked): links to other sites, and files they downloaded. Neither shows until the tracker has sent some.

A funnel is two to five pages a visit goes through in order, such as `/pricing` then `/signup` then `/thanks`. Funnels are a card on the Overview (`/overview`), after By weekday and hour. It starts with the first funnel's sentence ("Of 120 visits that reached /pricing, 9 got to /thanks. Most dropped off between /pricing and /signup."), then a chart for each funnel, with its name and a Remove button: a row per step against the first step's visits: the visits that got there in violet and, after them, those lost on the way in pale violet ("38,441 left"), the biggest drop stronger with its count in bold; then each step's count and its share of the first step, as the sentence counts. Type the pages on one line in the card and save; with a goal set, a funnel from the busiest page to the first goal is filled in already. With no funnel, the card says to type the pages a visit goes through, in order, and offers the field. The dashboard learns the saved funnels with the goals it loads at the start (the same KV read, no more calls); the Overview asks for their numbers only when it opens, one call and one query per funnel, and nothing when there is none. A step counts a visit when the visit viewed it, any time, after reaching the step before, so a visit that saw `/signup` before `/pricing` is counted at `/signup` only if it came back to it. Steps and goals match whatever the address's trailing slash or accents (`/pricing/` is `/pricing`). Under 30 visits at the first step, Lede says there are too few to say and picks out no drop. Funnels are saved for everyone, like goals, up to five per site. The sample data comes with one (the home page, then `/feeders`, then `/nests`) until you save your own.

The overview's Keywords card, right after where readers came from, shows what can be known about search, and says what can't: Google doesn't pass on what people searched for to find a site, so those words never reach Lede, and the card says so. A switch picks one of two lists (it opens on site searches, or on ads when only they have words); a sentence names the top word, the top 5 words follow, and "All N words" opens the rest in place. An empty list says how to fill it. The two lists:

- **Searched on your site:** the words people typed into the site's own search box, read from the page address of the results page (`?q=`, `?s=`, `?search=`, `?query=`, `?keyword=`, `?keywords=` or `?k=`) when the view arrives. Only the words are stored, as `?q=`; the rest of the address's query never is. A search box that sends its words some other way (in a form post, or only to a script) doesn't show up.
- **Words your ads paid for:** the `utm_term` on the link a visit landed from. Google Ads fills it in when an ad's link ends in `utm_term={keyword}`; other ad networks have their own placeholder.

Each word counts the visitors who used it, against the period before. Words are lowercased and trimmed, `+` and `%20` read as spaces, the result pages of one search (`?q=owls&page=2`) count once, and words are cut at 80 characters.

A note marks something you did on a day, such as "Posted on Hacker News" or "New homepage", in up to 80 characters. Pick a day on the visitors-per-day chart, on home or the overview (click it, or focus the chart, move with the arrow keys and press Enter; the day's hint says so) and write it; the note shows as a speech bubble under that day, on home too, and in What happened. Click the bubble to change or remove it. Notes are saved for everyone who opens the dashboard, one per day, dated in your time zone. When visitors moved to a new level that lasted, starting on a noted day or the day after, and that move makes at least half of the period's change, home's sentence says so: "Visitors rose 40% after you posted on Hacker News (Wed, Oct 7)." A noted day (or the day after) with at least 1.5 times the visitors of a usual day like it, and more above it than a usual day swings (twice the square root of the usual, and 5 at least), is said too: "Sat, Oct 17 had twice the visitors of a usual Saturday, the day you shared /owls in a Facebook group." Lede only says what came after; it never says your note caused it. A note that starts with something done ("Posted…", "Sent…") is told as what you did; any other is quoted as your note ("after your note “New homepage”").

A goal is a page you want visits to reach, such as `/signup`. Flag it from the Pages list or a page's view, or answer the question on home when a page looks like one ("Is /signup a goal, a page you want visits to reach?"). Select the flag again to stop tracking it. A goal is at most 200 bytes. With a goal set, home says under its sentence how many visits reached it, as counts under 50 visits ("3 of 40 visits reached /signup") and as a share from there, and names a source that did much better or worse: "1.3% of visits reached /signup; from Hacker News only 0.1%."

## Get the story by message

Lede can send the week's story every Monday, and a line when far more people than usual are on your site at once, to Slack, Discord or ntfy. Nothing is sent, and no stats are read for it, until you give it an address.

1. Make an incoming webhook: in Slack, an [incoming webhook](https://api.slack.com/messaging/webhooks) for a channel; in Discord, the channel's settings, Integrations, Webhooks, New Webhook, Copy Webhook URL; for ntfy, any topic address, such as `https://ntfy.sh/<a-long-name-only-you-know>`, then subscribe to it in the ntfy app.
2. Run `npx wrangler secret put ALERT_WEBHOOK` and paste the address.
3. Open the dashboard once, so the messages can link to it: Lede remembers the address it was last opened at. On a custom domain, or to link somewhere else, add `"DASHBOARD_URL": "https://stats.example.com"` to `vars` in `wrangler.jsonc` instead.

Both messages are on once the webhook is set. For only one, add `"ALERTS": "weekly"` or `"ALERTS": "spikes"` to `vars`.

- **The week's story**, Monday at 08:00 UTC: for each site, the same sentence home shows for 7 days, about Monday to Sunday (UTC) against the week before, then its [second line](#the-second-line) when Workers AI writes one, the visitor total, the source that sent the most visitors and the page that moved most (or was visited most), and a link to the dashboard's last 7 days. All sites go in one message, or a few in a row when it's longer than the webhook takes (2,000 characters on Discord, 4,096 bytes on ntfy), cut between sites. A schedule on the Free plan may make 50 requests, KV reads among them, and each site's week takes 6 to 9 queries (one more for each list when a week needs a query of its own, and a query Cloudflare refuses at first is asked again), one KV read for your notes (so the sentence can say what came after one, as home's does) and one Workers AI request, which is made only while there's room for it, so sites are told one at a time while there's room left for the message (about 6 sites, fewer on busy ones); any more, and a site whose queries run out of room, are named at the end ("Too many sites for one message, so a.org and b.org aren't in it.").
- **Spikes**, checked every 15 minutes: when at least 10 people are here now and that's both twice the usual and 10 more than it, it says how many, the page most of them are on, where most came from, and how many are usually here at this time of day, such as "42 people are on /blog/x of example.com right now, most from Hacker News. Usually about 3 at this time of day." The usual is the average of the same 5 minutes on each of the 14 days before, or on as many of them as the site has had data for (from its first event, looked up once and kept in KV as `added:<site>`); a site with less than 3 days of data gets no spike message. It names where most came from. At most two a day per site, at least 3 hours apart, so one long crowd is told once.

Slack gets `{"text": …}`, Discord `{"content": …}` (and pings nobody), and any other address the text itself in a `POST`, which is what ntfy expects. A webhook that fails is logged in the Worker's logs (see Deploy from the command line) and nothing else stops. The times are in `triggers.crons` in `wrangler.jsonc`; the spike check must stay `*/15 * * * *`, and any other schedule sends the week's story.

To see the messages without a webhook, run `npm run dev` and open http://localhost:8787/__scheduled?cron=0+8+*+*+1 (the story) or http://localhost:8787/__scheduled?cron=*/15+*+*+*+* (a spike): the terminal prints them, from the sample data. With `ALERT_WEBHOOK` in `.dev.vars`, they go to the webhook, which is a quick way to test it.

## The second line

Workers AI is optional. `wrangler.jsonc` binds it (`"ai": {"binding": "AI"}`); remove that and deploy, and home and the messages are as they were without it: `/api/sites` then says `insight: false`, and the dashboard doesn't even ask. A period with fewer than 30 visitors has too little to connect, and gets no second line.

- **What it's sent.** Lede works out the connections itself and sends them as numbered candidates (`factSheet` in `src/insight.js`), each joining two kinds of facts, in order of interest: a top page that's read longest or loads slowest, with its reading time and Web Vitals; a word searched on the site that names a top page; a source whose visits that began on one page rose or fell most; your note and that day's visitors against a usual day; a source whose visits bounce far more or less than the site's; and the source that rose fastest, with where its visits began. With them go the period, the total and home's sentence, so the line doesn't repeat it. It's rounded, so it changes only when the numbers really move: counts of 100 or more to 2 significant figures (1,240 is "about 1,200"), shares to whole percents, reading times to 10 seconds and page speed to 10 ms. Reading time, Web Vitals and search words (the top words the Keywords list shows) are asked for with the rest. Home doesn't need them, so building the sheet costs 2 queries of its own (search words and the words ads paid for come from one), and it's built at most once an hour per site and period: within the hour after the last try, the kept line stands as it is and no query is made. No visitor or visit IDs and no addresses, only paths and hosts. When nothing connects, nothing is sent.
- **Where it goes.** To `@cf/google/gemma-4-26b-a4b-it` on Workers AI, in your own Cloudflare account, with its thinking off (with it on, the thinking alone used up the answer's room). Cloudflare doesn't keep what Workers AI is sent or train on it. Lede doesn't use AI Gateway, which would log it.
- **What it's told.** Take the first candidate home's sentence doesn't already say and put it in one or two plain sentences, using only that candidate; never why something happened, nor that something you did caused it ("after your note" is fine); at most one practical suggestion about a slow page or a page many visits began on, starting "Worth checking:".
- **What's checked** (`problem` in `src/insight.js`), whatever it was told: every number, page, site and source named in the line must come from one and the same candidate, as written there or rounded from it (1,200 may be 1.2k, 130 seconds may be 2m 10s, and a share must be a share there too), so two true facts can't be joined into one that isn't; no word that says why (because, caused, due to, thanks to, led to, drove, resulted and the like); at most 2 sentences and 280 characters. A line that fails any check isn't shown, and the sentence stands on its own.
- **What it costs.** About 8 to 10 Neurons a line; the Free plan includes 10,000 a day. Each site and period keeps one KV entry, `insight:<site>:<days>`, with the line, the SHA-256 of the sheet it came from, when it was written and when Workers AI was last asked; it deletes itself after a day. A kept line is shown while it still passes the checks against today's sheet and is under 6 hours old, or for as long as the sheet is the same. Workers AI is asked again only when there's no entry, or when the sheet has changed and the last ask was an hour or more ago; an ask that came to nothing (no Neurons, busy, or a line that failed a check) counts as one, and each instance asks once at a time. So the most a site can cost is one ask and one KV write an hour for each period opened: 24 a day for 7 days and 24 for 30 days, 48 in all, about 480 Neurons and 48 of the Free plan's 1,000 KV writes (Cloudflare instances that ask in the same minute, before KV has passed on the other's write, can add one or two). That worst case needs the dashboard open every hour, all day, with the rounded numbers moving each time; a site whose numbers hold costs one ask a day per period, when the entry runs out. Once the day's Neurons are used, Workers AI answers 3036 until 00:00 UTC and the line is left out; nothing is billed. The week's story asks once per site.
- **When it fails** (no Neurons left, Workers AI busy, a line that failed a check), the Worker's logs say so once a day per instance, with what to do next, and the dashboard shows nothing in its place.

To show one site's stats to someone without giving them the password, click Share beside the site's name, then Copy link. The link looks like `https://lede.<your-subdomain>.workers.dev/s/Xk3…` and opens that site's dashboard read-only: no other sites, the goals' results without a way to change them, and a line saying it was shared by the owner. Stop sharing turns a link off; it can keep working for up to a minute after that, because each Worker instance keeps the list of links for a minute. Everyone who opens a link reads stats like you do, so their views count against the same daily allowance (see [Limits](#limits)).

Each event is one data point, indexed by site. The blob order is defined once in `src/schema.js`:
site, path, url, referrer, channel, visitor, visit, type, country, utm_source, utm_medium, utm_campaign, target, device, browser, utm_term.
New fields only go at the end, so rows already stored keep their meaning. `type` is `pageview`, `engagement`, `outbound` or `download`; rows from before there were other types are all page views, and every page-view stat filters on it. `url` (blob3) is the page's path, plus `?q=` and the words on a site search's results page; nothing else from the query is stored. Figures are doubles: `double1` is engaged milliseconds, `double2` scroll depth in percent, `double3` a page view's place in its visit (1 for the first, 2 for the second, 3 for any later one; 0 on other events and on rows from before it was recorded), and `double4` to `double6` the page's LCP and INP in milliseconds and its CLS times 1,000 plus 1, on engagement events (0 when the browser didn't measure it; CLS is one higher so a page that never shifts still counts). `double7` is when the page view started, in ms, on page views, engagement events and pings (0 on rows from before it was sent), and `double8` is 1 on an engagement event that says the page view was left (its tab hidden or closed, or a single-page app moving on; 0 on rows from before). Pings also carry the page view's engaged time and depth so far in `double1` and `double2`. `target` is the clicked link's host and path, without its query. `device` (blob14) and `browser` (blob15) are empty on rows written before Lede recorded them. `utm_term` (blob16) is the ad keyword of the page the visit landed on, cleaned as search words are (see Keywords above), and empty on rows from before it was collected.

### What each number means

- **Visitor:** a hash of a monthly salt + site + IP + user agent. IPs are never stored. Each month's salt is random and deletes itself from KV the day after the month ends, so IDs can't be linked across months, even by you. A visit is hashed with the salt of the month it started in, so one running past midnight on the 1st (UTC) stays one visit by one visitor. Someone who comes both before and after the 1st still counts as two visitors in a period that holds it; when only one of the two periods compared does, home compares visits instead of visitors.
- **Visit:** a visitor's page views from the clock hour the visit started. The tracker remembers that hour per tab, so a visit that runs past the hour stays one visit until half an hour passes without a page. A new tab starts from the current hour; after half an hour without a page, the next one starts a visit from that minute, so two visits in the same hour stay two.
- **Bounce:** the share of visits with a single page view. Each page view says whether it's the first, second or a later one of its visit, so visits and bounces stay right when Analytics Engine keeps only a sample (see Limits).
- **Time on site:** time between the first and last view of multi-page visits, divided by all visits.
- **Landed on / Left on:** the first and last page of a visit.
- **Source:** the site a visit came from (the referrer of the page it started on). With no referrer, a `utm_source`, `source` or `ref` tag on the landing page names it, with common short tags read as the site they mean (`fb` → `facebook.com`); with neither, it's Direct. The tracker keeps it in `sessionStorage`, so later pages of the visit still credit it, and a link within the site that carries a tag doesn't replace it. Redirectors, mobile hosts and Android apps go by the site's own name (`l.facebook.com` → `facebook.com`, `t.co` → `x.com`, `t.me` → `telegram.org`, `go.bsky.app` → `bsky.app`, `android-app://com.google.android.gm` → `mail.google.com`), and Google's and Yandex's country sites (`google.de`, `yandex.ru`) count as one source each; see `src/channels.js`.
- **Channels:** paid (ad click IDs, including `li_fat_id`, `twclid` and `dclid`, or a paid `utm_medium`), email (webmail, Outlook's Safe Links and Teams), AI assistants, search, video, social, referral, direct, from the referrer or, when the visit is tagged, its `utm_source` and `utm_medium`. Google Sites and Yahoo News aren't search. See `src/channels.js`.
- **Time on page:** how long a page view was in front of someone: the median over the views that sent an engagement event (half were shorter), so a few tabs left open don't pull it up. It only runs while the tab is visible and its window has focus, stops counting at 30 minutes, and a view under a second isn't counted. Time read after coming back to a tab counts too: the page view sends its totals so far each time the tab is hidden or closed, and once more when a single-page app moves to the next page, and each ping carries them as well, so a tab the phone closes without hiding it first still leaves how long it was read. After the first, a send needs 3 seconds more, a deeper scroll or a new Web Vital, so flicking between tabs sends nothing. Each page view counts once, with the largest totals it sent. Add `data-engagement="false"` to the script tag to turn it off, page speed with it.
- **How far down:** how far down the page the bottom of the window got, as a share of the page's height, averaged the same way. A page that fits on the screen is read to the end. It's taken on scroll, a second after the view starts, and when the tab is hidden or closed, but not when a single-page app moves on: by then the next page is usually drawn, and its height would be taken for the page being left. An endless page, which adds the next page below as you read and changes the address when you get there, holds several pages in one document, so the document's height says nothing about any one of them. Mark each page's element with its path, as the address shows it (`<article data-lede-page="/chapter-2">`), and each view is measured within its own element: a page scrolled past into the next one counts as read to the end, and the pages added above and below don't count.
- **Here now:** anyone whose last page view or ping was in the last 5 minutes. A tab that shows pings every 3 minutes, counted from its last page view or ping, so someone reading one page for a long while stays here, and in the same visit; a window in the background counts while its tab shows, a hidden tab doesn't, and coming back to a tab after 3 minutes or more pings at once. After 30 minutes with no scroll, click, key or touch the pings stop, so a tab left open isn't someone here; any of them starts the pings again. Hiding a tab, closing it or moving on in a single-page app takes that page view out at once (a glance under a second sends nothing, and drops out after 5 minutes as before); someone with another tab still showing is still here, and a tab shown again pings straight away. With the dashboard open, who is here is pushed to it as it changes (see `src/live.js` in Pieces), so the only wait left is Analytics Engine's for a dashboard that has just opened. Pings count nowhere else: not as views, visits or bounces.
- **Page speed:** Google's three Web Vitals, measured by the reader's browser and sent with the engagement event, so they cost no extra request or write: LCP (how long the page's main content took to show), INP (how long the page took to answer a click, tap or key) and CLS (how much the layout jumped while it loaded). Each page gets the 75th percentile of the views that measured it, which is how Google judges them, and says how few they were when under 30, rated good, needs work or poor: LCP under 2.5 s is good and over 4 s poor, INP 200 ms and 500 ms, CLS 0.1 and 0.25. Not every browser measures all three; a view counts only for those it did. Home mentions a page with many visitors whose LCP or INP is poor.
- **When a lasting change began** (for notes): the day that best splits both periods into a lower and a higher level, after each weekday is evened out against its own average; today and the last day of the period before aren't over, so they are left out.
- **Outbound links and downloads:** clicks (and middle clicks) on a link to another host, and on a link to a file such as a PDF, ZIP, DMG, EXE, CSV, Office document or audio and video file, on any host. Counted by visitors, credited to the page and the visit's source like a page view. The link's query is never sent, since links often carry a token or an email address, and parts of its path that look like an email, a long number that isn't a date, a UUID, a long hex string or a long token are left out; a file keeps its extension.
- **Devices:** phone, tablet or computer, from the user agent (`src/devices.js`). iPads on iPadOS 13 or later send the same user agent as Safari on a Mac, so most iPads count as computers; only older iPads, Android tablets and Kindles show as tablets. Chrome's `Sec-CH-UA-Mobile` header only settles an Android user agent that says neither phone nor tablet. Neither it nor the device is part of the visitor hash.
- **Browsers:** the family only, never the version: Chrome, Safari, Firefox, Edge, Samsung Internet, Opera, "Inside apps" (the browsers inside Instagram, Facebook, LinkedIn and other apps) and "Other browsers". Edge, Samsung Internet, Opera and apps also say Chrome, so they're checked first; Chrome and Firefox on iPhone count as Chrome and Firefox.
- **Countries:** Cloudflare's country for the request, stored as its two-letter code and shown by name.
- **Why bounce changed:** the change splits into where visitors came from (last period's bounce per source, weighted by this period's mix, minus last period's rate) and how each source behaved (its visits × its own change in bounce, over all visits). Whatever is left (other sources, sources new this period) is "everyone else", so the parts add up to the total.

### What isn't counted

Lede leaves out whatever isn't a person reading, and your own visits if you ask. The rules are in `src/bots.js`, `src/spam.js` and `src/collect.js`. A visit left out gets the same empty answer as one counted, so a script can't tell which rule caught it.

- **Your own visits:** run `localStorage.lede_ignore = 1` in the browser console on your site, and that browser is left out.

- **Cloudflare's Browser Run:** the browser that takes a page's picture sends an ordinary Chrome user agent from Cloudflare's own network, which the rules below keep, so it's known by the `cf-brapi-request-id` or `cf-brapi-devtools` header it always adds (no person's browser sends them). This drops anyone's Browser Run scripts, not only Lede's.
- **Bots by name:** user agents that say they're a crawler, a monitor, a headless browser or an HTTP library (`bot`, `spider`, `HeadlessChrome`, `curl`, `python`…); Cubot phones say "Cubot" and are kept. Cloudflare's verified-bot flag only reaches Workers with Bot Management, an Enterprise add-on, so Lede goes by the user agent and the network instead.
- **User agents no browser sends** (after [Pirsch](https://github.com/pirsch-analytics/pirsch)): 16 characters or fewer, more than 500, anything outside plain ASCII, one that is only an IP address, a UUID or a hash, a Firefox whose `rv:` doesn't match its version (except the `rv:109.0` Firefox 110–119 sent), and browsers older than any device that still updates: Chrome before 90, Firefox before 78, Safari before 12 and Internet Explorer before 11. The versions aren't checked for browsers that ship an old engine on purpose or run where it never updates: Android webviews (`; wv)`, whose engine belongs to the app, or to a system webview that phones without Google Play never update), the Chinese browsers and apps that bundle their own frozen Chromium (WeChat's TBS and XWEB, QQ Browser, the Baidu app, Quark, Sogou, and the MIUI, Huawei, OPPO and vivo browsers), UC Browser, Samsung Internet, smart TVs, Tesla, KaiOS, Pale Moon, SeaMonkey and Waterfox. Safari is judged by its `Version/`, so iOS in-app browsers (Instagram, Facebook, LinkedIn), which send none, and Android webviews, which send a fake `Version/4.0`, are left alone. The cost: Android 4.4 or older, iPhone 5 or older and OS X 10.10 or older aren't counted.
- **Data centres:** events from the networks of AWS, Google Cloud, Azure, Oracle Cloud, Alibaba Cloud, Tencent Cloud, DigitalOcean, Hetzner, OVHcloud, Linode, Vultr, Contabo and Scaleway (by `request.cf.asn`). People don't browse from servers, but scrapers do. Google's main network (AS15169) is left in, because Pixel's VPN and Google Fi use it, and so are Cloudflare, Fastly and Akamai's CDN, which iCloud Private Relay and similar privacy proxies exit through. Visitors on a cloud desktop (Windows 365, Amazon WorkSpaces) or a VPN hosted at one of those providers aren't counted. To count them, add `"KEEP_DATACENTER": "true"` to `vars` in `wrangler.jsonc`.
- **Referrer spam:** visits whose source is on [Matomo's referrer spam list](https://github.com/matomo-org/referrer-spam-list) (public domain), or a subdomain of one. The list is copied into `src/spam.js`, with the command to refresh it at the top. Its hosts are matched exactly, so a real site that only looks like spam stays.
- **More than 60 events a minute from one sender** (in `src/collect.js`): a sender is one browser (an address and a user agent) on one site, and one address counts for at most about 400 a minute, however many browsers share it. A reader sends a view and an engagement event per page, a few link clicks and a ping every 3 minutes; someone flicking to a new page every 5 seconds sends about 25 a minute. So 60 is never reached by a person, while a script or a page stuck in a loop stops counting within the minute, instead of using up the day's writes (see [Limits](#limits)). The rest of that minute isn't counted. The count lives in the Worker's memory, under a hash of the address, and is never written anywhere.
- **Global Privacy Control:** off by default, since Lede stores nothing that identifies a person. Add `"RESPECT_GPC": "true"` to `vars` and visits from browsers that send `Sec-GPC: 1` aren't counted (Brave and DuckDuckGo send it by default; Firefox and privacy extensions such as Privacy Badger when it's turned on).

### API

All stats routes take `site`, `days` (1–45), `tzName` (the viewer's time zone, such as `America/New_York`), `tz` (`Date#getTimezoneOffset()`, used when `tzName` is missing or unknown), and optional filters `path`, `referrer` (`""` = direct) and `channel`.

Days run from local midnight to local midnight in `tzName`, so the day the clocks change is 23 or 25 hours long (23.5 or 24.5 on Lord Howe Island), as it really was. With only `tz`, one offset is used for the whole period. Today is only partly over, so the previous period stops at the same time of day.

- `GET /api/summary` → visitors, visits, views, bounce, duration for the period and the one before; `sampled: true` when Analytics Engine kept only a sample of some of this period's views, and `prevSampled` the same for the period before; `split: {cur, prev}`, true when that period holds the start of a month (UTC), when visitor IDs start again; and, only when neither period has a view, `ever`: whether the site had any view in the last 90 days
- `GET /api/series` → the same metrics per day, plus each day's top source and how many visitors it sent
- `GET /api/breakdown?dim=path|entry|exit|referrer|channel|country` (referrer rows also carry the channel the host falls in)
- `GET /api/audience` → `country`, `device` and `browser` lists (visitors, visits, views, bounce, duration, and last period's), and `partial`: `"cur"` or `"prev"` when that period has visits stored before devices and browsers were recorded, else `null`. Devices and browsers then carry no previous figures.
- `GET /api/flows` → visitors by the source a visit came from and the page it landed on, with that pair's visits and the visits that left after one page
- `GET /api/firsts` → the day each page and source was first seen in the period
- `GET /api/hourly` → visitors per hour of the period, counted in whole days back from today's local midnight, so today's hours match the clock even after a daylight-saving change earlier in the period
- `GET /api/live` → visitors in the last 30 minutes, with who is active in the last 5
- `GET /api/live/ws` (a WebSocket) → the same answer, pushed as it changes; `404` without the `Live` Durable Object
- `GET /api/conversions?goal=/signup&goal=/thanks` → visits per source, and how many of them viewed a goal page
- `GET /api/engagement` → per page: page views that sent an engagement event, average seconds on the page, `median` time per view (ms) and share scrolled, with last period's, and page speed: `lcp`, `inp` (ms) and `cls` (as its score), each the 75th percentile of the views that measured it, or `null` when none did, and `lcpN`, `inpN` and `clsN`, how many views measured each (only views with a tap or click measure INP). With `path`, the page also gets `reach`: the share of those views that got at least 10%, 20%... 100% of the way down, counted in the same query
- `GET /api/next?path=/pricing` → for each period: views of the page, how many were the visit's last (`left`), how many visits viewed it, and the pages viewed straight after it, most first; `sampled` says when a period's figures come from a random sample of visits
- `GET /api/links` → `outbound` links and `downloads`, each with visitors, clicks and last period's visitors
- `GET /api/keywords` → `site` (words searched on the site) and `paid` (ad keywords), each a list of `{key, visitors, prev}` with last period's visitors (`null` when no one used the word then), most used first, up to 100
- `GET /api/shot?site=&path=` → today's picture of the page as a jpeg, or `{og, why}`: the page's share picture (or `null`) and why there's no picture: `budget` (the day's browser time is used), `permission` (the token can't take pictures), `busy` (Cloudflare's browser didn't answer and spent no browser time; asking again a minute later tries again) or `failed`
- `POST /api/signin` with `{"password"}` sets the cookie; `POST /api/signout` clears it
- `GET /api/insight` → `{text}`: the [second line](#the-second-line) under home's sentence, or `204` when there's none (no Workers AI, fewer than 30 visitors, no Neurons left, or a line that failed a check)
- `GET /api/sites` → the sites Lede counts, `demo`, and `insight`: whether to ask for the second line; `POST /api/sites` with `{"site": "example.com"}` adds one
- `GET /api/goals` → the site's goals, its notes, its tab icon (`icon`, 0 to 8, or null for the automatic one) and its funnels too (as `GET /api/funnels` gives them), so the dashboard reads them with one request and knows whether the Overview has funnels to read; `PUT /api/goals` with `{"goals": [...]}` saves them
- `GET /api/notes` → the site's notes, `[{day: "2026-10-16", text: "Posted on Hacker News"}]`, oldest first; `PUT /api/notes` with `{"day", "text"}` adds or replaces that day's note; `DELETE /api/notes?day=2026-10-16` removes it. Each answers with the notes as they now are. A change is one KV write, and one that changes nothing writes nothing; the newest 100 notes are kept.
- `PUT /api/icon` with `{"icon": 3}` keeps that colourway for the site's tab icon; `{"icon": null}` goes back to the automatic one
- `GET /api/funnels` → the site's funnels, each a list of steps; `PUT /api/funnels` with `{"funnels": [["/pricing", "/signup"], ...]}` saves up to five, each two to five different paths of up to 200 characters
- `GET /api/funnel?steps=/pricing&steps=/signup&steps=/thanks` → `steps`, and `cur` and `prev`: the visits that reached each step in order, this period and the one before. One SQL query reads both periods, and only views of the step pages. The filters don't apply.
- `GET /api/shares` → the read-only links, newest first; `POST /api/shares` with `{"site": "example.com"}` makes one; `DELETE /api/shares?token=…` stops one. Password only.

### Limits

- Messages read stats only once `ALERT_WEBHOOK` is set. The spike check is one Analytics Engine query per site every 15 minutes (96 a day), plus one for the usual crowd when 10 or more people are here and a message could go out, so 96 to at most 192 a day per site; once per site, one more finds when its data starts, and a message that would name a source that isn't a well-known site asks whether it sent anyone before. The week's story is 6 to 9 queries and one KV read per site once a week. The free limit is 10,000 queries a day, and loading the dashboard home is 8. They write to KV only when a spike message goes out (at most 2 a day per site, of the free 1,000), once per site for when its data starts, and when the dashboard's address changes.
- Opening a page's view is one more Worker request, for its picture; the first open of a page each day also lists and writes KV once (no list once the day's browser time is spent), and while Cloudflare's browser is busy, each open of that page a minute or more later lists and writes once more and spends a few seconds of Browser Run time (at most 5 minutes a day, of the free 10). Without a picture it fetches the page once a day for its share picture and writes that to KV.
- Workers AI writes the [second line](#the-second-line): about 8 to 10 Neurons each, of the free 10,000 a day, and one KV write for each ask; at most one an hour per site and period opened, 48 a day per site in the worst case.
- Analytics Engine keeps data for 3 months, so the API caps a span at 45 days (the comparison doubles that); the dashboard offers 7 or 30.
- Every event is one Analytics Engine write, and every request one Worker request; a single-page app's page view goes in the same request as the engagement event of the page it left. Engagement adds roughly one write per page view, and one more each time a reader leaves the tab and comes back to read on (that send, plus the ping that brings them back to "here now"); link clicks add a few more. So a site writes about twice as many data points with it on, more where readers switch tabs a lot. The Workers Free plan allows 100,000 Analytics Engine writes and 100,000 Worker requests a day: about 100,000 page views a day without engagement, or about 50,000 with it. Past that, add `data-engagement="false"` to the script tag, or move to Workers Paid.
- One sender (a browser on one site) is counted for at most 60 events a minute, and one address for about 400 (see [What isn't counted](#what-isnt-counted)), so a script firing many events a second can't spend the day's 100,000 writes in minutes. It costs no KV writes and no Analytics Engine reads: each Worker instance keeps the counts in memory for up to 10,000 senders, the oldest dropped first. Cloudflare runs several instances, so a sender spread over them can get past 60 a minute, and one sending at exactly the cap all day could still write 86,400 events; the cap stops floods, not a slow, steady script. To count across instances in a location too, add Cloudflare's rate limiter to `wrangler.jsonc` (Lede uses it when it's there; Cloudflare doesn't say whether the Free plan includes it, so it isn't on by default):
  `"ratelimits": [{ "name": "BEACON_LIMIT", "namespace_id": "1001", "simple": { "limit": 60, "period": 60 } }]`
- At very high volume Analytics Engine samples data. View counts, engagement averages and medians are corrected with `_sample_interval`; distinct visitor counts are not. In a sampled period, visits are counted from first page views and bounces from visits without a second one (`double3`), each weighted by its sample, so a visit that lost a view to sampling isn't counted as a bounce. When this happens in either period, home says so under the sentence.
- Each comparison (summary, days, breakdowns, flows, engagement, link clicks) is one SQL query covering both periods, with each row labelled by period. Lists keep each period's top rows (100 for breakdowns, 200 for engagement and links); SQL here has no `LIMIT BY`, so the query asks for more (ten times as many for breakdowns and those lists, twice as many for flows) and Lede trims each period. When one period fills that whole answer, as after a tenfold change in traffic on a site with hundreds of pages, the other period is asked for on its own.
- The `Live` Durable Object is SQLite-backed, which the Workers Free plan includes, with 100,000 requests a day of its own. While no dashboard watches, each Worker instance asks it once a minute at most per site, on the first event that comes; while one does, every page view, ping and hidden tab is a request, and a row written. Opening the socket is two requests and one query.
- How long Analytics Engine takes to show a write isn't documented. `scripts/ae-lag.mjs` measures it on your own Lede: `ANALYTICS_TOKEN=… node scripts/ae-lag.mjs --lede https://lede.<your-subdomain>.workers.dev --site example.com`, from your own computer (data-centre addresses are dropped). Each run is one ping on a page no one has, which shows in "here now" for 5 minutes.
- Read-only links share the SQL API's 10,000 reads a day on the Free plan: every viewer's stats reads count against it like yours. Making or stopping a link is one KV write.
- Countries, devices and browsers are one query: visits grouped by all three at once, then added up per list. A visitor's hash covers their IP and user agent, so each visitor sits in one group and the lists add up. Device and browser add two short blobs to each event, not more writes.
- What readers do next needs the page view after each view of the page, and this SQL has no window functions, joins or `IN (subquery)`. So `/api/next` asks twice: first for the visits that viewed the page in both periods (by the first 12 characters of their ID, ordered by ID, which is a hash, so the first ones are a random sample), then for every page view of up to 250 of those visits per period, written into the query as a list. The Worker sorts each visit's views by time, counts a page viewed again straight after as one view (a reload), and pairs each view of the page with the next one; when nothing follows, the reader left. 250 visits per period is what fits the SQL API's 10 KiB; past that the dashboard says the figures come from that many visits picked at random. A visit that runs from one period into the next counts as leaving at the border.
- Stats answers are kept for 60 s (15 s for live) in each Worker instance and, on a custom domain, in Cloudflare's edge cache too (Cloudflare documents the Cache API for custom domains, not `workers.dev`). The browser keeps each for up to a minute too, privately (`Cache-Control: private`), so going back to a view asks for nothing.
- SQL here can't take one parameter out of an address, so the site search query sends back each search address once per visitor (up to 20,000 a query, both periods together) and the Worker reads the words. A site with more searches than that in a period gets lists from the first 20,000.
- Filter values reach SQL hex-encoded (`hex(blob2) = '…'`), because the SQL API documents no string escaping.
- The stats are read from the dataset named `lede`, as `analytics_engine_datasets` in `wrangler.jsonc` creates it. If you rename it there, set `DATASET` in `vars` to the same name; when the dataset is missing or holds nothing yet, the dashboard says so.

## Measuring changes

Every change is measured before it goes in. Performance work must improve the numbers; any other change must keep them.

```sh
npm run bench            # this working copy against the commit in bench/baseline.json
npm run bench:compare    # judges it; exits 1 on a regression
```

`scripts/bench.mjs` runs both versions without Cloudflare: the Worker in Node with stand-ins for Analytics Engine and KV that count every query and write (`bench/fakes.mjs`, `bench/server.mjs`), and the dashboard and tracker in headless Chrome Canary with the CPU slowed 4x. It records:

- **Bytes**: `t.js` as sites receive it (`public/t.js`, so run `npm run tracker` first), and everything the dashboard can load, raw, gzip and brotli. Any increase is a regression.
- **Counts**: Analytics Engine queries, `/api` calls, page pictures and their browser time, KV reads, writes and lists, and Workers AI asks and the tokens they send (a token for about every 4 characters; Neurons follow tokens) per dashboard page, with the second line's sheet counted apart, since it's built at most once an hour per period; requests, writes and KV use per visit, and the `Live` object's requests per visit while no dashboard watches, plus requests and writes for a visit that leaves the tab and comes back, and one through a single-page app; and the same for one spike check and one week's story, run with an alert webhook set (`bench/cron.mjs`). These are what the free limits count, they don't vary between runs, and any increase is a regression. The judge also prints what the schedules take a day (96 spike checks and a seventh of the week's story), and how much a day the rest leaves room for.
- **Timings**: the Worker per visit and per stats answer, what `t.js` adds to a page, and how long the dashboard home takes to draw and how long it blocks. The two versions run in turn, rep after rep, and the judge looks at the ratio of each pair. A timing is worse when the bootstrap 95% range of the median ratio sits wholly above the threshold for that metric (in `bench/noise.json`, twice what unchanged code swings, at least 5%) and the medians differ by more than 0.05 ms. A range that crosses the threshold is inconclusive: rerun before believing it. A Worker answer over 5 ms fails on its own, to stay well under the 10 ms of CPU free Workers get.

A regression blocks the change. First make the change pay for itself, with a leaner way to do the same thing or a saving elsewhere in the same change, never by taking out what it's for. Only when that fails can the owner allow it, after seeing the numbers, and that should be rare; the commit message then names what got worse, by how much, and why it's worth it. Put the before and after numbers that changed in the commit message. When a change makes Lede smaller, cheaper or faster, record the new baseline in the same commit with `node scripts/bench.mjs --save-baseline`. After a Chrome Canary update or a move to another machine, measure the noise again: `node scripts/bench.mjs --aa` then `node scripts/compare.mjs --noise bench/runs/aa.json`. Runs land in `bench/runs/`, which git ignores.
